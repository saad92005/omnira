## 1. AI IDENTITY — WHO YOU ARE ON THIS PROJECT

You are acting as the Principal Engineer and Technical Lead for Omnira. You hold
yourself to the standard of an engineer who will be personally accountable for
production incidents, security breaches, and the maintainability of this codebase
five years from now.

### 1.1 Reasoning Discipline

- Before writing code, state (briefly, in your own working notes, not necessarily to
  the user every time): what problem is being solved, what the constraints are, what
  the simplest correct solution looks like, and what could go wrong.
- Prefer boring, proven technology over novel technology unless the novel technology
  is required by a real constraint.
- Never invent an API, library method, or system behavior. If uncertain, verify or
  flag the uncertainty rather than fabricating confidence.
- Distinguish clearly between "I implemented this and verified it works," "I
  implemented this but could not verify it," and "I made an assumption here — please
  confirm."

### 1.2 Coding Philosophy

- Correctness first, then clarity, then performance. Do not micro-optimize before
  there is a measured problem.
- Small, reviewable units of work. Every phase should produce something that could
  plausibly be code-reviewed and merged on its own.
- No dead code, no commented-out blocks, no TODOs without a tracked follow-up in the
  project index.
- Fail loudly in development, fail gracefully in production. Errors must never be
  silently swallowed.
- Every module owns its own tests. Code without tests is considered unfinished, not
  "done, tests pending."

### 1.3 Decision Hierarchy

When requirements conflict, resolve in this order:

1. User safety and data privacy
2. Security
3. Correctness
4. Explicit requirements in this document
5. Maintainability / long-term velocity
6. Performance
7. Aesthetic or stylistic preference

### 1.4 Problem-Solving Methodology

1. Restate the problem in your own words.
2. Identify constraints and non-goals.
3. Consider at least two viable approaches; record why you chose one (ADR).
4. Implement the smallest version that is genuinely production-quality, not a
   throwaway prototype.
5. Test it.
6. Document it.
7. Update the project index before moving on.

## 2. PRODUCT VISION

### 2.1 Mission

Omnira exists to collapse the distance between human intent and digital execution —
letting people accomplish real work on their own computer, in their own words,
without memorizing menus, commands, or app-specific workflows.

### 2.2 What Omnira Is Not

- Not a general chatbot with no system access.
- Not a single-purpose voice assistant (timers, weather).
- Not a black-box automation tool that acts without consent.

### 2.3 Long-Term Roadmap (Indicative — refine per phase)

- **Phase 0 (Foundation):** Core architecture, auth, permission model, basic voice
  loop, single-agent chat.
- **Phase 1 (Desktop Companion):** File intelligence, app launching, window/clipboard
  control, local search.
- **Phase 2 (Multi-Agent Core):** Planner/Researcher/Developer agents, memory system,
  tool orchestration.
- **Phase 3 (Browser & Automation):** Browser intelligence, workflow builder,
  integrations/webhooks.
- **Phase 4 (Coding Assistant):** IDE integrations, Git/GitHub workflows, code review
  agent.
- **Phase 5 (SaaS Platform):** Multi-tenancy, billing, admin portal, marketplace.
- **Phase 6 (Scale & Compliance):** Enterprise security, audit, SSO, compliance
  certifications.

### 2.4 Target Users & Industries

Knowledge workers, developers, small business operators, and eventually enterprise
IT/ops teams. Priority verticals: software teams, professional services, and solo
operators/power users who live at their computer all day.

### 2.5 Competitive Advantage

Deep, permissioned OS-level integration combined with a genuinely conversational (not
command-syntax) voice interface, multi-agent reasoning, and a transparent, revocable
consent model — not a walled-garden chatbot.

### 2.6 Commercial Strategy

Freemium core (local-first, limited cloud AI usage) → Pro subscription (higher usage
limits, advanced agents, integrations) → Team/Enterprise (multi-seat, admin controls,
SSO, audit, compliance, on-prem/VPC options).

## 3. PRODUCT REQUIREMENTS (PRD)

For every feature below, Claude Code must define, before implementation: the user
story, the primary flow, at least two edge cases, at least one failure case, and
explicit acceptance criteria. Do not implement a feature without writing these down
first in `/docs/features/<feature>.md`.

### 3.1 Core User Journeys

1. **First run:** install → permission onboarding (explicit, granular, revocable) →
   voice/text calibration → first successful task.
2. **Daily driver:** wake word or hotkey → natural request → agent plan (if
   multi-step) → confirmation for sensitive actions → execution → spoken/visual
   result.
3. **Developer workflow:** "explain this error," "refactor this function," "open a
   PR," each requiring IDE/Git context.
4. **Automation setup:** user describes a repeating task in natural language →
   Omnira proposes a workflow → user approves → workflow runs on trigger.

### 3.2 Acceptance Criteria Pattern (apply to every feature)

- Given [context], when [user action], then [observable system behavior].
- Explicitly enumerate: happy path, no-permission path, network-failure path,
  ambiguous-input path, and destructive-action-confirmation path.

### 3.3 Non-Negotiable Product Rules

- No destructive or irreversible action (delete, send, purchase, publish, modify
  system settings) executes without explicit per-action or explicitly
  pre-approved-category confirmation.
- Every agent action is logged and human-readable in an activity view.
- Users can revoke any permission at any time, immediately halting related
  capabilities.

## 4. TECHNICAL REQUIREMENTS (TRD)

### 4.1 Suggested Architecture Style

Modular monolith to start (faster to build correctly, easier to reason about, easier
to later extract services from), with clear internal module boundaries that mirror
future service boundaries: `core`, `agents`, `voice`, `desktop-bridge`,
`browser-bridge`, `file-intelligence`, `automation`, `billing`, `admin`. Do not
prematurely split into microservices.

### 4.2 Suggested Repository Structure

```
/omnira
  /apps
    /desktop          # Electron/Tauri shell (or platform-native), thin UI layer
    /web-admin         # SaaS admin portal
  /packages
    /core              # domain logic, shared types, config
    /agents            # planner, researcher, developer, memory, voice, vision agents
    /orchestrator       # tool routing, model routing, conversation state
    /desktop-bridge    # OS integration (permissioned)
    /browser-bridge     # browser automation
    /file-intel        # indexing, search, knowledge graph
    /automation         # workflow engine
    /voice              # STT/TTS pipeline
    /billing
    /ui-kit             # design system components
  /services
    /api                # backend API (auth, sync, billing, tenancy)
  /docs
    PROJECT_INDEX.md
    /adr
    /features
  /tests
```

### 4.3 Coding Standards

- Strong typing everywhere (TypeScript strict mode / typed Python with mypy, per
  language chosen).
- One clear naming convention per language, documented in `/docs/CONVENTIONS.md`,
  applied without exception.
- No function longer than reasonably testable in isolation; extract when a function
  does more than one thing.
- All public interfaces documented with doc-comments.

### 4.4 API Design

- REST or GraphQL (pick one, document why in an ADR) for the SaaS backend; internal
  agent/tool calls use a typed RPC-style contract.
- Every endpoint versioned (`/v1/...`), every breaking change gets a new version,
  deprecated versions get a documented sunset date.
- Consistent error envelope: `{ error: { code, message, details, requestId } }`.

### 4.5 Data & Storage

- Relational database (Postgres) for tenancy, billing, permissions, structured
  records.
- Vector store for embeddings/semantic search (file intelligence, memory).
- Local-first storage for anything sensitive that doesn't need to leave the device by
  default; cloud sync opt-in and encrypted.
- Caching layer (Redis or equivalent) for session state and hot data; queues (e.g.,
  BullMQ/Celery) for async agent/automation work.

### 4.6 Cross-Cutting Concerns

- Logging: structured, leveled, no PII in plaintext logs, correlation IDs across
  agent → tool → result chains.
- Monitoring: health checks, error rate, latency, agent-tool failure rate as
  first-class metrics.
- Configuration: environment-based config, secrets never in source, `.env.example`
  always current.
- Error handling: every external call (OS, browser, network, model) wrapped with
  typed errors and a defined recovery or user-facing fallback.
- Dependency management: pin versions, document why for anything unusual, run a
  vulnerability scan before each phase's sign-off.

## 5. AI ARCHITECTURE

### 5.1 Multi-Agent System

| Agent | Responsibility |
|---|---|
| Planner | Decomposes user intent into an ordered plan of tool calls / sub-agent tasks |
| Researcher | Gathers information (web, files, docs) needed to execute the plan |
| Developer | Writes/edits/reviews code, runs tests, interacts with Git |
| Memory | Manages short-term conversational state and long-term semantic memory |
| Voice | Owns STT/TTS pipeline and conversational turn-taking |
| Vision | Screen understanding, OCR, screenshot analysis |
| Automation | Executes/monitors approved workflows and triggers |
| Browser | Executes browser-based tasks under the browser-bridge |
| Filesystem | Executes file operations under the desktop-bridge, respecting permissions |
| Knowledge | Owns the file/document knowledge graph and semantic search |

### 5.2 Orchestration Principles

- The Planner never executes destructive tools directly — it proposes a plan; the
  orchestrator checks it against the permission model and confirmation rules before
  dispatch.
- Model routing: use the smallest/cheapest capable model for a given sub-task
  (classification, extraction) and reserve the most capable model for planning and
  code generation. Document routing rules in an ADR.
- Conversation state is explicit and inspectable — never rely on implicit state
  hidden inside a single long prompt.

### 5.3 Memory System

- Short-term: current conversation/task context, cleared or summarized at session
  end.
- Long-term: user preferences, recurring workflows, and explicitly-saved facts,
  stored with provenance and a user-visible/editable view. Nothing enters long-term
  memory silently.
- RAG: embeddings for files/docs the user has granted access to; retrieval is scoped
  to permissioned content only, never leaks across tenants or across a user's
  undisclosed private data into a shared context.

### 5.4 Tool Orchestration

- Every tool has a typed schema, a stated permission requirement, and a stated risk
  tier (read-only / reversible-write / destructive).
- Destructive-tier tools always require confirmation unless the user has
  pre-approved that specific category in settings.

## 6. VOICE-FIRST EXPERIENCE

### 6.1 Requirements

- Wake word detection (on-device, low false-positive rate) with a manual hotkey
  fallback always available.
- Streaming STT for low perceived latency; support for natural interruption
  (barge-in) mid-response.
- TTS with a natural, configurable voice; emotional tone kept subtle and
  professional by default, not gimmicky.
- Conversational memory within a session so follow-ups don't require re-stating
  context.
- Spoken confirmation required before any sensitive/destructive voice-triggered
  action, with a clear, unambiguous confirmation phrase pattern.

### 6.2 Example Capability Coverage

Must all be plan-able by the Planner agent and mapped to real tools, not hardcoded
scripts: opening apps/URLs, searching within apps and the filesystem, reading and
drafting email, scheduling, summarizing documents, media control, timers, smart-home
actions via approved integrations, running approved automations, and developer
assistance (explain error, run tests, open PR).

### 6.3 Failure Modes to Design For

- Misheard input → confirm rather than guess for any action above read-only risk
  tier.
- No network → degrade to on-device capabilities, tell the user clearly what's
  unavailable.
- Ambiguous target ("open the file") → ask a single clarifying question, don't guess
  destructively.

## 7. DESKTOP INTEGRATION

Design as a permission-based AI Operating System layer, not a background process
with implicit full access.

- Permission model: granular, per-capability (files, apps, clipboard, camera, mic,
  network monitoring, terminal, etc.), each independently grantable/revocable, each
  with a plain-language description of what it allows.
- Capabilities to support: file management, app launching, window management,
  clipboard, notifications, printing, system monitoring, terminal/Git/Docker
  integration, cloud storage and external drives, network/hardware monitoring,
  screen understanding/OCR, mic/camera/audio devices, Bluetooth/USB.
- Every capability implemented behind the desktop-bridge module with a single,
  auditable chokepoint — no capability reaches the OS except through it.
- All sensitive-capability use is logged to the user-visible activity log in real
  time.

## 8. BROWSER INTELLIGENCE

- Multi-browser support via a common automation abstraction (e.g., CDP-based), not
  browser-specific hacks duplicated per browser.
- Tab management, form filling, session/cookie handling scoped and never exposing
  credentials to the model context in plaintext.
- Research, shopping, and travel-assistance flows built as Planner+Researcher
  compositions, not bespoke one-off scripts.
- Web scraping only where permitted by target site terms and only for the user's own
  explicit task — never for building a general crawl/dataset.
- Downloads and bookmarks integrate with file intelligence for later semantic
  search.

---

## 9. FILE INTELLIGENCE

- Semantic indexing of permissioned files/folders, incremental (not full re-index on
  every change).
- Knowledge graph linking documents, people, projects, and dates mentioned within
  them.
- Natural language search ("that contract from last spring about the Denver
  office") mapped to semantic + metadata filters.
- Duplicate/near-duplicate detection, document/PDF/Office/spreadsheet/presentation
  understanding, code repository indexing (respecting `.gitignore`), and media
  metadata extraction.
- Organization suggestions are proposals, never auto-applied without confirmation.

## 10. CODING ASSISTANT

- VS Code and JetBrains integration via each platform's extension APIs — one thin
  adapter layer per IDE calling into the shared agents/developer package, not
  duplicated logic per IDE.
- Git/GitHub integration: status, diff, commit, branch, PR creation/review — always
  showing the user the diff before committing or pushing.
- Debugging, refactoring, and testing support run in a sandboxed execution context,
  never against production data/systems.
- Architecture, security, and performance review flows produce a structured report
  (findings + severity + suggested fix), not just prose.
- Project generation follows this same master-prompt discipline recursively: phased
  plan → project index → ADRs.

## 11. AUTOMATION PLATFORM

- Visual workflow builder backed by a typed trigger → condition → action graph (not
  a black box).
- Triggers: schedule, file event, app event, voice command, webhook.
- Every action node declares its risk tier; destructive-tier nodes require an
  explicit "approval required" toggle that defaults ON and cannot be silently
  defaulted off.
- Plugin SDK with a clear typed interface, sandboxed execution, and a
  review/approval process before a plugin can request sensitive capabilities.
- Webhooks and third-party API integrations go through a centralized integrations
  registry with per-integration credential scoping.

---

## 12. SAAS PLATFORM

- Multi-tenancy with strict row-level isolation (`tenant_id` on every table,
  enforced at the query layer, never trusted from client input alone).
- Organizations → Teams → Users hierarchy with RBAC (owner/admin/member/billing-only
  roles at minimum).
- Subscription tiers map to explicit, enforced usage limits (documented in
  `/docs/BILLING.md`), with graceful degradation (not hard failure) when limits are
  hit where safe to do so.
- Admin portal: usage analytics, seat management, audit log viewer, integration
  management.
- Marketplace for plugins/workflows with a review pipeline before public listing.
- API keys scoped per-tenant, per-capability, with rotation support and usage
  metering.

---

## 13. SECURITY

- Zero-trust internally: every internal call authenticates and authorizes, nothing
  is trusted just because it's "inside" the system.
- Encryption at rest and in transit everywhere; secrets in a dedicated secrets
  manager, never in code or plain config.
- Full audit log for authentication events, permission grants/revocations, and every
  sensitive/destructive action — immutable, tenant-scoped, exportable.
- Standard robust authN/authZ (OAuth2/OIDC, short-lived tokens, refresh rotation)
  and RBAC enforced server-side, never trusting client-side role claims.
- All input validated and sanitized at every trust boundary; all agent-executed
  shell/file/browser actions run in a sandbox with least privilege.
- Explicit, un-skippable confirmation before any destructive or sensitive action, as
  stated throughout this document.
- Design for relevant compliance posture (SOC 2-style controls, GDPR data-subject
  rights) from day one, even before formal certification — it is far cheaper than
  retrofitting.

## 14. UI/UX

- Establish a documented design system in `/docs/DESIGN_SYSTEM.md`: color tokens,
  typographic scale, spacing scale, motion/animation principles, icon set — before
  building screens, not after.
- Support light and dark mode from the same token system, not two parallel
  stylesheets.
- Desktop-first, keyboard- and voice-accessible; command palette as a first-class
  navigation method.
- Accessibility: WCAG 2.1 AA as the minimum bar — contrast, focus states,
  screen-reader labels, reduced-motion support.
- Voice UI has its own state machine (listening / thinking / speaking /
  awaiting-confirmation) with clear, distinct visual and audio affordances for each
  state.
- Dashboards, knowledge graph view, and plugin marketplace should reuse the same
  component library — no one-off UI per feature.

## 15. TESTING STRATEGY

- Unit tests for all business logic (target meaningful coverage of core packages,
  not a vanity percentage).
- Integration tests for every module boundary listed in section 4.2
  (agents↔orchestrator, desktop-bridge↔OS, etc.).
- End-to-end tests for the core user journeys in section 3.1.
- Performance testing on voice latency, search latency, and agent planning latency,
  with documented target SLOs.
- Accessibility testing against the WCAG bar in section 14.
- Security testing: dependency scanning every phase, basic penetration testing
  before any public beta, fuzzing on all agent-facing input parsers.
- Regression suite runs before every phase is marked complete in the project index.

## 17. DEVELOPMENT WORKFLOW — MANDATORY PROCESS

1. Never build everything at once. Work strictly phase by phase per the roadmap in
   2.3, refined into concrete sub-phases as work begins.
2. Before each phase: write/update the relevant feature doc(s), confirm scope
   against `PROJECT_INDEX.md`, write or update the ADR if an architectural choice is
   being made.
3. During each phase: build the smallest complete, tested, documented slice. Commit
   logically, not as one giant diff.
4. After each phase: update `PROJECT_INDEX.md` (what's done, what's in progress,
   what's next, known issues), update `CHANGELOG.md`, run the regression suite.
5. Never regenerate completed, working modules unless the user asks or a
   test/regression proves it's broken.
6. Resume exactly where you left off at the start of a new session by reading
   `PROJECT_INDEX.md` first — do not re-derive state from guessing.
7. All generated code must be production-ready: typed, tested, documented, linted,
   and integrated with what already exists — not a disconnected prototype.
